三、自进化双回路详解（你的核心目标）

Loop-A · 测试集自动进化（反向优化“评测数据”）

白话评测跑完后，把“失败案例”当种子，自动生成新的、更难/更多样的测试题，经过验收后发布成新版本测试集。评测集自己越长越刁钻。

为什么需要静态测试集会被被测对象“刷分”过拟合；失败驱动的进化能持续发现新安全盲区，且每单位预算发现率可量化（research_plan 主指标）。

例子agent_execution 发现 10 条“Agent 泄露了私有日历”的失败 → Loop-A 生成 50 条同类但换了场景/工具的变体 → 八门控验收 → 发布 v2 测试集。

  • 当前状态：🔴 仅在 loop-a-local-harness 分支，fixture 级原型
  • 已有：test_generator（本地模板，未调付费 API）、admission 八门控（来源许可/可重放/良性可解/私有规则/去重/多样性/留出隔离/审核）
  • formal_qualified 恒 false，run 返回非零阻断——还没真正生成过可发布测试集
  • 待补：合入 main、真实测试集生成器、八门控执行器、dataset-version 发布、留出集隔离落地

Loop-B · 评测方法进化（反向优化“评测方法”）

白话针对“某个被测对象分数低”，受控地改它的提示词/策略（不是让模型自己乱改），配对跑基线 vs 候选，过门槛后封存决策。方法被反向打磨。

为什么需要同一套评测方法会对不同被测对象暴露不同短板；受控进化让“方法”随证据迭代，同时守住“不自动部署、unknown 不补通过”的安全边界。

例子某产品 ASR 偏高 → 写一条 prompt recipe（白名单改动）→ 配对跑基线 vs 候选 → 8 门槛（安全/回归/成本/配对置信…）→ 封存 promote，但不自动上线。

  • 当前状态：🟡 main 已实现“受控控制平面”
  • 已实现：target-build（白名单 recipe，禁改命令/端点/凭据）、register（资产哈希+失败谱系）、preflight（只读校验，不调 API）、evaluate（配对执行，sha256 防篡改）、compare（8 门槛）
  • 缺口（protocol 里 not_implemented 5 项）：模型生成式候选优化、非 agent_execution 轨道调度、部署、自动回滚、轮次控制
  • 关键差距：现在是“人写 recipe，机器受控比较”，还不是“AI 根据失败自动生成优化”——这正是你要的“反向优化方法”所需补的那块

四、4 人分工方案（你 = 总体框架与设计）

先说人怎么切：你（总体框架）+ 4 个成员，共 5 人。你不定具体某条评测轨道的业务代码，你定的是所有人都要遵守的“铁轨”（数据格式、接口、质量门），以及最后拍板矛盾谁听谁的。4 个成员每人认领一块垂直模块包，互相之间不读对方代码、只看“标准产物”交接——就像工厂流水线，上一道工序只管把标准件递到下一道，不管下一道怎么用。

5.6 评测分类体系（默认体系 + 可插拔 · 可修改变量）

分类体系是我们自己提出的默认参考体系，不是写死的锁。设计原则：① 体系可插拔——每个体系在 protocol/ 下有一份自包含的定义文件（id + 维度编码 + 层级 + 适用 modality + 逐维定义，如 protocol/default_taxonomies.yaml），运行时由 config/taxonomies/ 的注册项引用；改体系=改配置，不动 schema 代码；② 默认体系由我们提供（LLM 19 维 + Agent 5 域），仅作 benchmark 无原生体系时的兜底；③ 原生体系优先——官方 benchmark 自带体系（AgentBench 任务族、InjecAgent 注入子类、ASRBench 错误码等）直接注册引用，不强行套我们的体系；④ 跨体系对照（crosswalk）是可修改的配置变量——只为统一报告提供“映射到默认体系”的派生视图，改不改、怎么映射都由用户编辑，不影响原始数据。
体系性质维度定义（仓库内路径，外部协作者可直接访问）如何接入
默认体系 · LLM
taxonomy=default-llm		 默认兜底（我们提出） safety_l1 × safety_l2，19 个二级伤害维度（1–19）；定义在仓库内 protocol/default_taxonomies.yaml（含逐维定义）+ 编码注册表 protocol/taxonomy_registry.yaml；人读版 docs/default_taxonomies.md（待成员1 落地） benchmark 无原生体系时，题目归到该体系，每模型按 19 维出分

benchmark 原生体系

crosswalk 配置		 可调变量（派生视图） 任意体系 → 默认体系的映射表（如某 benchmark 的“prompt injection” → default-agent 的 2.x） 纯配置，用户可改；不映射也能跑，仅统一报告时用到

铁律反转：不再要求“新 benchmark 必须映射到我们的两套维度”。原生体系是一等公民，我们的体系只是默认兜底与统一报告的参考系。新增/修改体系 = 改 config/taxonomies/ 注册（可热插拔），不需要改 schema 代码，也不需要总体框架逐条审批。

定义出处与外部可访问性：两套默认体系的机器可读定义已落地于 protocol/default_taxonomies.yaml 与 protocol/taxonomy_registry.yaml；人读版 docs/default_taxonomies.md 尚未创建，待成员1 落地。外部协作者通过 https://github.com/StrawberryTreea/agent-safety-harness 即可访问机器可读定义，不依赖任何本地路径。定义原文出自《2026大模型与智能体安全测评白皮书》第 4 章；白皮书 PDF 与 668,820 条评测样本仅存于作者本地，不随仓库分发，正式引用以 PDF 原文为准。

5.8 LLM 角色与配置（统一到 harness/config/llm_roles.json · 密钥只走环境变量）

harness 要“接指令输入 + 自动行动 + 自进化”，底层都靠 LLM，但不同用途必须用不同角色、隔离配置。现有代码把“被评对象”散在 harness/config/models.json 与 llm_eval 的 MODELS 两处，且缺少“harness 大脑”与“生成器”两个角色。统一为三角色配置：每条目字段 provider / base_url / api_key_env / model / temperature / max_tokens / timeout_seconds / system_prompt，密钥只存环境变量名（api_key_env），绝不进文件。关键架构决定（你定的）：CLI 与 harness_driver 都是“交互壳”，底层都调同一个 tool_registry 函数层；harness_driver 直接调 Python 函数，绝不 shell 出 CLI 字符串。
角色含义配置现状字段用途
under_test
被评对象		 被测的模型 / Agent（llm_qa 与 agent_execution 轨的目标） ✅ 已有，但散在两处：llm_eval 的 evaluator_config.models + harness/config/models.json（--agent model:<id>）。成员1 须合并到 llm_roles.json 的 under_test 组 被测 Agent 的 system_prompt 即它的“指令输入”，它据此自动调工具行动（这是**被测对象**的行动，不是 harness 的）
harness_driver
harness 大脑		 解析自然语言指令 → 规划 → 直接调 tool_registry 函数自主串联全流程（拉 benchmark→搭沙箱→跑评测→评分→分析→触发自进化） 🔴 缺失，需新增。落位 agent_safety_harness/driver/（与 adapters/evaluation/sandbox/importers 平级的子包）。当前 CLI 是手敲命令，无 driver LLM；要支持“自然语言描述即可行动”必须加此角色 接收用户高层自然语言指令（如“复现 AgentBench 并构建隔离环境跑一轮自进化”），产出结构化 plan 后逐条调注册函数执行；可带 system_prompt 约束它只调已批准函数（对应质量门“不部署/不自动晋升”）
generator
自进化生成器		 Loop-A 出题（从失败生成更难测试题）/ Loop-B 未来“模型自动优化方法” 🟡 现混在 Loop-B 的“目标”配置里（evolution/target_executor.py 的 MODEL_CONFIG_FIELDS）。注意：当前 target-evolution-contract.md 明写“不使用 LLM 发明优化”——要改成用户要的“自动”，必须独立出此角色 吃 failures.jsonl 生成新 TaskSpec（Loop-A）或生成 candidate 配方（Loop-B）；与 under_test 物理隔离

铁律：under_test 与 generator 必须物理隔离——出题/优化用的 LLM 绝不能是被测对象，否则自进化结果自欺欺人。harness_driver 默认只读已批准函数清单（tool_registry 的白名单），不能越权执行未注册动作；它调函数而非 CLI 字符串，保持结构化数据在内存中流转、避免 subprocess 序列化损耗。密钥一律 api_key_env 引用环境变量，配置文件中不得出现任何 key 明文。

5.8.1 harness_driver 落位与内部构成

「搭沙箱、跑评测、触发自进化」等所有“行动”本质是 tool_registry 里的一个函数，harness_driver 只负责理解意图 + 选函数 + 按序调用 + 看返回决定下一步，本身不重新实现任何引擎能力。内部构成（成员1/4 共建）：
子模块职责输入 → 输出
agent_safety_harness/registry.py
（包级，CLI 与 driver 共用）		函数注册表：每个能力装饰注册为 {name, input_schema, output_schema, fn}；提供 list()（白名单给 driver 看）/ call(name, **kwargs)引擎函数 → 统一可调用目录
driver/planner.py把自然语言/半结构化指令拆成有序函数调用 plan（可含分支：如“若 benchmark 无本地源则先 bench_intake”）自然语言指令 + 已批准函数清单 → 结构化 plan（list of {fn, args}）
driver/executor.py顺序/条件执行 plan，调 registry.call；遇到 build_sandbox 等耗时动作可挂后台并回传状态plan → 各阶段产物（同函数层） + 自进化触发信号
driver/nl_bridge.py调用 harness_driver 角色 LLM，把指令→plan；受 system_prompt 约束只产已批准函数自然语言 → plan（json）

两种用法等价：手敲 pipeline_cli bench-intake X && build-sandbox X && run-capture X，与对 driver 说“复现 X 并构建隔离环境跑一轮”最终都落到同一批 registry 函数。前者给人用，后者给“想用自然语言的你/协作者”用，底层零重复。
