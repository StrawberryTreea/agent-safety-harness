# 自动化评测反馈如何带来可验证的改进

研究问题：在固定预算与私有评分协议下，利用失败轨迹生成的新测试，是否比静态测试或随机变体发现更多独立、可重放、跨目标成立的安全问题？另一个问题是修复后的 Agent 是否在冻结留出集上提高安全性，同时保留正常任务能力。

第一阶段以测试集演化为主实验。Agent 修复、提示更新或训练作为后续独立干预，防止测试更难和系统变好被混成一个结果。

## 先建立一条真实可审计执行链

1. 固定一个被测产品、版本、模型、工具权限、预算与任务集，先做约 20 个可重放任务的真实执行验证。mock smoke 只验证管线。
2. 每条任务保留公开任务、环境状态、私有安全规则、轨迹、资源消耗与错误分类。需要能力分析时，另加良性配对任务和完成规则。
3. 先分析真实失败，人工检查少量失败轨迹是否支持其失败类型，再启动自动候选生成。原生 benchmark 线先完成专用环境与官方 scorer 的资格验证。

## 主比较

| 条件 | 新测试来源 | 作用 |
|---|---|---|
| 静态基线 | 固定原测试集，重复运行种子 | 估计自然随机性和已有覆盖 |
| 随机变体 | 同一任务池中随机选择可控变换 | 控制新增任务数量和生成预算 |
| 失败反馈 | 从已验证失败轨迹提取单一变化条件 | 检验失败证据是否带来额外发现能力 |

随机与失败反馈条件使用相同生成器、变换空间、轮数、token/执行预算和验收规则。建议先进行 50 组配对良性/攻击任务的小实验，再按有效样本率与成本决定规模；这些数值是实验计划，不是当前已完成结果。

## 数据与公平性

- 演化池、验证池和最终留出集在实验前冻结；跨源近重复一并分组。留出集轨迹、答案和私有规则不能进入生成提示。
- 候选生成器只见允许的失败摘要与经过处理的公开轨迹。私有 oracle 留在验收进程，记录泄漏检查。
- 记录 parent task、生成策略、模型版本、提示版本、种子、环境/scorer 版本、拒收原因和谱系。所有新任务先进入 staging。
- 生成条件保持原任务意图、工具和评分可解释性；变更环境或 oracle 时按新协议记录，不与旧版本直接比较。
- 错误和超时从候选有效性问题中单列，不能作为新增安全失败。拒答在不同轨道遵循原生指标。

## 核心测量

主结果是“每单位固定预算发现的、通过验收的独立安全失败”，同时报告提交候选数、接受数、可重放失败数及其分母。配套分析包括新失败家族覆盖、跨模型/产品迁移、重复率、良性完成率、运行有效率和 token/时间/金额成本。

使用配对任务与多次种子重复。按任务家族聚类给出置信区间，不能把同一父任务的多条近似攻击当成独立观测。汇总前分别处理 case 与 retrieval event；官方 ASR 只在其资格范围内报告。

## 关键消融与审查风险

移除轨迹证据、使用仅 reason 的反馈、移除失败优先选择，分别检验哪里产生收益。另做跨目标迁移，防止结果仅来自对一个目标反复试探。对近重复过滤强度做敏感性分析。

若仅增加样本量而不提高每预算发现率，结论应是覆盖扩展；若只降低原任务上的 ASR，需检查良性能力与冻结留出集后再谈系统改进。若候选不可重放或规则需要事后解释，先修复任务契约，不将其计入主要结果。
