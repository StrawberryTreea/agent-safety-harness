# 决策权、缺席与长期不上线（5 人团队的连续性机制）

> **配套文档**：[GitHub 协作规范](github_collaboration.md)（日常怎么提 PR）· [分工与推进顺序](work_assignment.md)（每人做什么）· [名册数据](roster.json)（机器可读的代理表）
>
> **这份文档回答一个问题**：**王浩有最终决定权，那么万一有人临时有事、有人长期不上线，项目会不会卡住？谁接手？**

---

## 0. 两句话结论

1. **王浩的最终决定权不依赖任何其他人在线**——他是唯一 admin，配置、分支保护、CODEOWNERS、权限都在他手里，别人离线不影响他拍板。
2. **谁都能独立提交自己的 PR**——仓库已取消"必须有人 approve 才能合并"的门槛，CI 全绿就合上。
   CODEOWNERS 的作用因此从"谁能批"变成了"**谁该知道**"：每个目录配 2 个知情人（主 owner + 代理人），
   改动到那儿会自动通知到人。

**这两套是独立的**：王浩离线 → 仲裁权按名册代行；其他成员离线 → 其目录由代理人接手、其 issue 自动改派。

---

## 1. 王浩的绝对权，具体指什么

### 1.1 唯一 admin，配置权不经过任何人

| 事项 | 谁能做 | 说明 |
|---|---|---|
| 改分支保护规则（加/减必过检查、开/关强推） | **只有王浩** | 其他 4 人是 `write`，改不了保护规则 |
| 改 `.github/CODEOWNERS`（谁被知会哪个目录） | **只有王浩** | 同上 |
| 增删协作者、调整他人权限 | **只有王浩** | 成员退出/新加入由他操作 |
| 合并任何 PR（哪怕 CI 未跑完） | **只有王浩** | admin 身份可强制合并；正常路径不需要任何人 approve |
| 直接推 `main`（绕过 PR） | **只有王浩** | 保护规则对 admin 生效，但 admin 可自行关闭保护再推 |
| 契约（schema / registry / protocol）口径裁决 | **只有王浩** | CODEOWNERS 知会 + CI 标记，双重提醒 |

**为什么用 admin 权限而不是"指定人"**：admin 是 GitHub 原生的最高权限，转移不了也伪造不了，比"口头约定谁能拍板"可靠。

### 1.2 绝对权怎么用：三条硬规矩

绝对权是为了**保证项目不停摆**，不是为了让流程消失。用的时候遵守这三条：

1. **优先走 PR**。日常改动还是提 PR、还是等 CI 必过。**不需要等任何人 approve**——
   5 人小组里多一道签字就多一天的等待（2026-11-04 已把分支保护的 approve 门槛取消）。
2. **只有这三种情况才用强制合并**：
   - CI 因外部原因长时间跑不完，而改动本身风险可控 → 先在 PR 里写明再强合，事后补跑 CI；
   - 契约口径分歧久拖不决 → 王浩直接给结论并合并（结论要写进 PR 描述或 issue）；
   - 线上事故级问题 → 强制合并 + 事后补记录。
3. **每次强制合并必须留痕**：在 PR 里写清"为什么绕过 CI、谁被绕过、影响什么"。留痕比权力本身更重要——否则半年后没人记得当初为什么破例。

### 1.3 明确不设的东西

- **没有"谁能批准谁能批准"的多层会签**。5 人团队，多层会签只会制造等待。
- **没有"必须有人 approve 才能合并"的门槛**。谁都能独立提交，CI 绿就合。
- **没有强制所有人在线的机制**。不打卡、不日报、不要求秒回（见协作规范第 7 节）。
- **没有"王浩休假就停摆"的机制**。仲裁权有代行路径，见第 3 节。

## 2. 有人临时有事（几天内回来）

### 2.1 不用改任何配置

因为**每条目录都配了 2 个知情人**（主 owner + 代理人）：

```
/harness/src/agent_safety_harness/   @deep-fry-xiaopengyou @DylanWu6
                                     ↑ 刘轲(主)              ↑ 代理人
```

| 情况 | 结果 |
|---|---|
| 主 owner 不在，其目录的 PR | 代理人会被自动提醒，改动照样合上 |
| 主 owner **就是 PR 作者** | GitHub 不把作者列为自动评审人，所以代理人会被提醒——不会有人被漏掉 |
| 代理人也不在 | 王浩被提醒；合并不受影响（没有 approve 门槛） |

**关键点**：**没有人会因此卡住合并**。CODEOWNERS 现在决定的是"谁该知道"，
不是"谁能批"。配 2 个人的理由只有一个：**保证至少另一个人被提醒到**——
因为 GitHub 不会把 PR 作者列为自动评审人，只配 1 人时若那人正好是作者，就完全没人知情了。

### 2.2 名册里写死了每个人的代理人

`docs/roster.json` 是唯一权威（不是这张表，是那个文件）：

| 成员 | 负责目录 | 代理人 | 代理人能接什么 |
|---|---|---|---|
| 王浩 | docs / protocol / references / tests / scripts | 一迪 | 契约分歧仲裁、口径裁决；**不含**仓库权限与分支保护变更 |
| 刘轲 | harness 核心 / registry / schema / sandbox / config | 伦锋 | registry 六函数编排、driver 侧调用接线；schema 字段级改动要回仲裁 |
| 辰浩 | federated_asr_benchmark（产品评测） | 一迪 | failures.jsonl 字段口径、四轨分析接线；ASR 口径要回仲裁 |
| 一迪 | llm_eval / result_analysis | 刘轲 | 数据接入、来源哈希校验；统计结论要回仲裁 |
| 伦锋 | evolution / orchestrator / driver | 一迪 | CI 门禁、driver 编排；闸门策略与预算口径要回仲裁 |

**代理人 ≠ 授权扩大**。代理人接手的是**未完成的工作**（接 issue、继续做）。在 CODEOWNERS 里，
他作为该路径的第二知情人——**知情权不是审批权**，合并权本来就不在任何人手上（CI 绿即可合）。

### 2.3 临时有事要做的三件事（10 分钟内）

1. 在自己的 issue 上留一句"休假 X 天，回来看 Y"——不用报备，写清楚就行。
2. 手上的 open issue 改派给代理人（`gh issue edit <编号> --add-assignee <代理人>`）。
3. 如果有 PR 还没人看：在 PR 里 @ 一下代理人，或等他有空——**PR 不会因此卡住**。

**不需要**改 CODEOWNERS、不需要改权限、不需要通知任何人。

## 3. 有人长期不上线（超过 30 天）

### 3.1 自动发现：巡检脚本

```bash
python scripts/oncall_roster.py            # 只出报告，不改任何东西
python scripts/oncall_roster.py --apply    # 改派 issue + 刷新看板
```

它做三件事：
1. 查 GitHub API，取每个成员**自己 authored** 的 commit / issue / PR 的最新时间（**只算自己的产出**，被别人 @ 或被指派 issue 不算活动——否则一个长期不上线的人会因堆积的指派看起来"很活跃"）。
2. 按阈值判定：无活动 **14 天 = 预警**，**30 天 = 需移交**。
3. 输出报告（JSON + Markdown），`--apply` 时把需移交成员的 open issue 改派给代理人，并刷新仓库里的「在岗与代理看板」issue。

**新成员基线**：名册里记了 `joined` 日期。加入 3 天还没提交的人，按"加入日"起算，不算"长期不上线"——避免刚上手就被判缺席。

### 3.2 判定阈值与动作

| 状态 | 条件 | 动作 | 谁执行 |
|---|---|---|---|
| 在岗 | < 14 天 | 无 | — |
| 预警 | ≥ 14 天 | 提醒；建议本人确认是否继续参与 | 巡检脚本出报告 |
| 需移交 | ≥ 30 天 | ① open issue 改派代理人 ② CODEOWNERS 中该成员的条目换成代理人 ③ 必要时移除仓库权限 | ①②脚本自动 ③王浩手动 |

**为什么阈值是 14 / 30 天**：14 天覆盖正常假期和期末考试；30 天基本可以判定人已经离场。阈值在 `docs/roster.json` 里可改。

### 3.3 王浩本人长期不上线

王浩是唯一的 admin，**admin 权限无法转移**（GitHub 限制）。所以分两种情况处理：

| 情况 | 谁能做什么 |
|---|---|
| 王浩短期不上线（几天） | **什么都不用做**。其他 4 人各有代理人覆盖，照常推进。仲裁类问题挂起等他回来。 |
| 王浩长期不上线（> 30 天） | **一迪代行仲裁权**（名册里 `backup` 字段），范围限于契约分歧裁决与口径把关。**仓库权限与分支保护变更暂缓**——因为只有 admin 能做，等他回来处理。 |

这条是刻意设计的：**不制造"影子管理员"**。5 人团队里再开一个 admin，密钥、权限、误操作的风险都要翻倍，而收益只是王浩不在时能改配置。改为：**代理只代行"判断"，不代行"权限"**。

### 3.4 成员退出（主动离开）

一次性动作，王浩手动做：
```bash
gh api --method DELETE repos/StrawberryTreea/agent-safety-harness/collaborators/<账号>   # 移除权限
```
然后：把其 CODEOWNERS 条目换成代理人 → 把 `docs/roster.json` 里该成员改成 `status: "left"`（或直接删掉条目）→ 把其 open issue 改派代理人。

## 4. 这套机制怎么被验证

不靠"文档写了就以为生效"，靠三处可执行的检查：

| 检查 | 在哪 | 怎么跑 | 失败意味着 |
|---|---|---|---|
| 名册一致性 | `tests/test_oncall_roster.py` | `python -m unittest tests.test_oncall_roster` | 有人没配代理人 / id 重复 / 代理指向自己 |
| CODEOWNERS 覆盖度 | 同上（`codeowners_coverage`） | 同上 | 某目录知情人少于 2 人 → 该目录改动可能无人被提醒 |
| 单测总数 | CI `Portable checks` | PR 自动跑 | — |

`scripts/oncall_roster.py` 在每次运行时也会自己检查 CODEOWNERS 覆盖度，**不达标会写进报告的"需要处理的动作"里**。
